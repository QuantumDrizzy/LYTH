# ADR-0028 step 5 -- the protocol for the falsification sweep of P1-P4

Frozen before the first sweep launch. `docs/prereg/ADR-0028.step5.PREREG_SHA256.txt` records the
hash of this file and of `tools/split_sweep.py`, which implements it, and the commit they were
frozen at. The predictions themselves are ADR-0028's `P1`-`P4`, frozen at
`docs/prereg/ADR-0028.prereg-frozen.md` and not repeated or edited here. What this file adds is
what the ADR left open: which counters, how many runs, in what order, and **what counts as a
pass**, so that no threshold is chosen after a number is seen.

## What is measured

* **The control.** `examples/hadamard.lyth` at `-n 4194304`: the same body on eight contiguous
  buffers of 2^22 floats (16 MB each). This is the kernel `hadamard_q` is claimed to match, and
  `hadamard_q` at `w = n/2` is the same kernel with the addressing written as a split.
* **The split kernel.** `examples/hadamard_q.lyth` at `-n 8388608` (four buffers of 2^23 floats,
  32 MB each, 2^22 pairs) for `w = 2^q`, `q = 0 .. 22`: every qubit of the register, 23 widths.
  Both kernels move 32 B per pair by the compiler's derived model; both walk 2^22 pairs; both
  touch 128 MB, past the 34 MB L2.
* **One binary, one machine file.** `target/release/lyth.exe` built from the commit recorded in
  the results, `fixtures/machine/sm_120.json`, the inputs of `lyth_lang::inputs` (deterministic).
  The sweep refuses to run on a dirty tree.

An erratum, recorded here and not by editing the frozen text: ADR-0028 says "16 MB re + 16 MB im".
At `N = 2^23` amplitudes each buffer is 2^23 f32 = 32 MB. The working set the two kernels share is
128 MB either way, which is what "past the L2" needed.

## What was seen before this was frozen

Three single runs, to see that the tooling works, and nothing else: `lyth run --time 50` at
`-n 8388608` for `w = 8` and `w = 1` (both about 388 GB/s, spread 76-78%; the control at
`-n 4194304`, `--time 30`, gave 385 GB/s and 79%), and one `ncu` launch at `w = 8` (DRAM read
16.0 and write 14.0 B/pair, L2 32.0 B/pair). The thresholds below are not derived from them: `tol`
is the 5% used throughout the earlier ADRs, and the rest are the numbers in ADR-0028 and its
progress note (1, 2, 8, `w >= 8`). What the runs do show is that the spread of one process is
large with the desktop attached to the GPU, which is why the run-to-run spread across rounds
sets `eps` and not the within-process one.

## Counters (bytes)

`ncu` on the one launch `lyth run` makes without `--time`, default cache control (flush before
the kernel), **three launches per configuration** in three rounds whose order is shuffled by
`random.Random(28)` like the timing rounds, the **median per counter** taken:

`lts__t_bytes.sum`, `dram__bytes_op_read.sum`, `dram__bytes_op_write.sum`, each divided by 2^22 to
give bytes per pair. The three are kept apart because they answer different questions (ADR-0015):
what the L1s asked the L2 for, and what crossed the memory controller, which the L2 may change.
Three launches, not one, because how many written sectors the L2 keeps varies from launch to
launch, and a verdict on a 5% tolerance should not rest on a single draw of it.

## Time

`lyth run --time 200` (10 warm-up runs it discards itself), one process per sample, **R = 7
rounds**. Every round runs all 24 configurations, in an order drawn by `random.Random(28)` and
different in each round, so a drift of the machine cannot line up with a width. Each process
yields a median; a configuration's time is the median of its 7 process medians, and its
**run-to-run spread** is `(max - min) / median` of those 7. No process is discarded. Clocks are
not locked and the desktop shares the GPU (a compositor, browsers, overlays): that is the
conditions, and it is why the threshold below has a floor.

## Verdicts, fixed now

Let `c` be the control, `x(w)` a width, `bytes(k)` its measured bytes per pair, `t(k)` its time,
`tol = 5%`, and `s_c` the control's own spread. `eps = max(tol, s_c)`.

* **P1, payload invariance.** PASS if for every `w` the measured DRAM bytes per pair
  (`read + write`) of `x(w)` are within `tol` of the control's. Reported beside it, and judged
  separately: whether the control itself is within `tol` of 32 B/pair. The frozen text says
  "measured DRAM traffic stays 32 B/pair"; the L2 may keep writes (ADR-0015's known limit), so if
  the control is not near 32 the *absolute* claim is reported as **not confirmed as stated**, and
  the invariance verdict stands on its own.
* **P2, the bus step.** Three results, all published:
  * **shape:** PASS if `lts(w)` is within `tol` of `lts(c)` for every `w >= 8`, exceeds
    `lts(c) * (1 + tol)` for each `w` in `{1, 2, 4}`, and is non-increasing in `w` across the
    whole sweep, where a rise of up to 1% between neighbouring widths is counter noise and
    allowed. ("Monotonically as `w` halves" is read as non-decreasing towards small `w`, so a
    plateau below 8 is allowed by this reading and named as one.)
  * **magnitude, refined:** PASS if `lts(w) / lts(c)` is within `[1.8, 2.2]` for `w` in
    `{1, 2, 4}` (the 2x the progress note derived from `view_index`).
  * **bound, frozen:** PASS if it is at most 8 for every `w`.
* **P3, time.** With `r(w) = lts(w) / lts(c)`, the measured bus ratio, and `T(w) = t(w) / t(c)`:
  * `w >= 8`: PASS if `|T(w) - 1| <= eps`.
  * `w` in `{1, 2, 4}`: PASS if `T(w) <= max(1, r(w)) * (1 + eps)`. Reported beside it: `T(w)`
    against 2 (the refined figure) and 8 (the frozen bound).
* **P4, correctness.** Every `lyth run` in the sweep must print `BIT-EXACT`. One `verify FAILED`
  is a P4 failure at that width, on the PTX back end. (The emulator half was recorded at step 4:
  20 launches, all bit-exact; it is not re-run here.)

## What is not claimed

No absolute bandwidth beyond the machine file's baseline; no claim about any GPU but this one;
no claim about `N` other than 2^23; nothing about the Unibit back end's speed (its low-width
path is one f32 per instruction, a `[KNOWN_LIMIT]` already recorded). `ncu` measures bytes and
does not time the kernels; the timing rig measures time and does not read counters. A number from
one is never used as if it came from the other.

## Publication

`docs/prereg/ADR-0028.step5-results.json` holds every raw number. The ADR's progress notes get
the table and the verdict of each prediction, **whichever way it went**, beside the unedited
frozen predictions. A failed prediction is written as one, with the counter that says so.
